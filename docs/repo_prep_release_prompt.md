## 🎯 План подготовки репозитория (6 этапов)

Выполняй подготовку строго последовательно, проверяя каждый шаг.

### Этап 1: Репозиторная гигиена и проверка безопасности

1. **Сканирование секретов и чувствительных данных**:
   - Убедись, что `.env` исключён из Git:
     ```bash
     git ls-files .env .env.* | grep -v "\.example"
     ```
     Если `.env` отслеживается, выполни `git rm --cached .env` и проверь `.gitignore`.
   - Проверь файл `.env.example`: в нём должны быть **только плейсхолдеры** (`your_token_here`), никаких боевых ключей Supabase `service_role` или токенов Discord-бота.
   - Выполни поиск по кодовой базе на случайные хардкоды токенов или секретов:
     ```bash
     git grep -iE "service_role|bot_token|supabase_key|password=" -- "src/"
     ```

2. **Очистка от мусора и артефактов сборки**:
   - Удали системные файлы ОС (`.DS_Store`, `Thumbs.db`) из индекса и дерева:
     ```bash
     find . -name ".DS_Store" -delete
     git rm --cached -r -f **/.DS_Store 2>/dev/null || true
     ```
   - Проверь `.gitignore`: должны игнорироваться каталоги `bin/`, `obj/`, `artifacts/`, `local.db`, `.idea/`, `.vscode/`, `TestResults/`.
   - Запусти полную очистку временных файлов сборщика:
     ```bash
     dotnet clean MedTracker.slnx
     ```

3. **Инспекция текущего рабочего дерева (Working Tree)**:
   - Проверь `git status -s`.
   - Все незавершённые изменения (локальное хранилище, видимость курсов, переключатели регистрации) должны быть логически сгруппированы и оформлены в атомарные коммиты по Conventional Commits.

### Этап 2: Синхронизация версий и релизных метаданных

1. **Повышение версии проекта до 1.0.1**:
   - Обнови `Directory.Build.props`:
     ```xml
     <!-- Версионирование для v1.0.1 релиза -->
     <Version>1.0.1</Version>
     <AssemblyVersion>1.0.1.0</AssemblyVersion>
     <FileVersion>1.0.1.0</FileVersion>
     ```
   - Обнови манифест Android `src/Med.Android/Properties/AndroidManifest.xml`:
     - Инкрементируй `android:versionCode` (например, с `1` на `2`).
     - Задай `android:versionName="1.0.1"`.

2. **Формирование `RELEASE_NOTES.md`**:
   - Переведи описание в статус релиза `1.0.1`.
   - Отрази в `RELEASE_NOTES.md`:
     - **Новые возможности (v1.0.1)**:
       - Двухэтапная регистрация: первичный старт без пароля и email с хранением в локальной SQLite.
       - Привязка облачного аккаунта (миграция данных из SQLite в Supabase).
       - Упрощённое управление курсами: переключатель «Бессрочный приём» vs курсовой приём с выбором даты окончания.
       - Уведомления: двухэтапный шедулинг (за 5 минут и в момент приёма) с отменой при подтверждении/пропуске.
       - Сохранение аватара при миграции профиля.
     - **Исправления безопасности и стабильности**:
       - Устранение уязвимости Shell Injection (RCE) в десктопных уведомлениях.
       - Безопасное формирование путей к медицинским файлам (защита от Path Traversal).
       - Исправление потери дневных доз в `DoseEventMaterializer`.
       - Корректная работа прогресс-бара дня (сохранение карточек в статусе «Выполнено»).
       - Переход на системные будильники `AlarmManager` на Android вместо in-memory `Task.Delay`.
       - Защита от Cross-Tenant утечек через фильтрацию Realtime.
     - **Известные ограничения**:
       - Discord/Telegram боты — интеграция серверной части отключена по умолчанию, подготовлен клиентский UI.

3. **Актуализация документации и README**:
   - Проверь `README.md`: обнови схему разделов приложения (раздел «Курсы» встроен в лекарства).
   - Убедись, что в `docs/` файлы отражают актуальное состояние (`1.0.1_update_plan.md`, `work_report.md`, `bugfix_report.md`).
   - Удали упоминания устаревших удалённых DTO-классов.

### Этап 3: Целостность базы данных и миграций

1. **Проверка SQL-миграций в `supabase/migrations/`**:
   - Проверь порядок и таймстампы файлов миграций.
   - Убедись в наличии:
     - `20261001000000_realtime_add_tables.sql` (добавление `medications`, `courses`, `schedules` в публикацию `supabase_realtime`).
     - `20261002000000_allow_permanent_courses.sql` (снятие constraint `courses_has_end`).
   - Проверь, что все таблицы имеют `ENABLE ROW LEVEL SECURITY` и корректные RLS-политики на `auth.uid() = user_id`.

2. **Синхронизация схемы локальной БД SQLite**:
   - Проверь `src/Med.Infrastructure/LocalStorage/LocalDatabase.cs`:
     - Таблица `courses` в SQLite не должна иметь constraint, запрещающий `ends_on IS NULL`.
     - Все типы колонок должны совпадать по смыслу с PostgreSQL (`TEXT` для UUID и ISO-дат, `INTEGER` для enum/days).
