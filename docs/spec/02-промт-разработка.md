# Задача

Ты — senior .NET инженер. Построй персональное приложение для приёма лекарств
и хранения медкарты. Работаем итеративно, стадиями. Не пиши весь проект одним
ответом: на каждой стадии дай код, объясни решения, дождись подтверждения.

Целевые устройства с GUI: Android и macOS.
Windows и Linux GUI не делаем — там пользователь читает уведомления в
десктопных клиентах Telegram и Discord.

## Ключевое ограничение этой фазы

Интерфейс делается ПОЗЖЕ другим человеком. Сейчас нужен только технический
каркас UI: голые списки, голые формы, кнопки без стилей, без темизации,
без анимаций, без иконок, без адаптива. UI существует ровно для того, чтобы
руками проверить работу логики.

Из этого следует главное архитектурное требование:
**ни одной строки бизнес-логики в View или code-behind.**
Вся логика — в отдельных проектах, за интерфейсами, покрытая тестами.
Слой UI должен удаляться целиком без поломки остального решения.

# Стек

- C# на .NET 10, nullable enabled, warnings as errors
- Avalonia UI 12 — единый UI-код для Android и macOS
- CommunityToolkit.Mvvm — ObservableObject, RelayCommand, ObservableProperty
- Microsoft.Extensions.DependencyInjection + Options + Logging
- NuGet-пакет `Supabase` (именно `Supabase`, НЕ устаревший `supabase-csharp`)
  — Auth, Postgres, Storage, Realtime
- Supabase: Postgres + Storage + Edge Functions + pg_cron + pg_net
- HttpClient через IHttpClientFactory — для прямых вызовов API мессенджеров
- xUnit + FluentAssertions для тестов доменной логики
- Единственный не-C# код в проекте: SQL-миграции и Edge Functions на

Своего домена и своего сервера нет. Все публичные URL — это URL
Edge Functions вида `https://<project-ref>.supabase.co/functions/v1/<name>`.

# Доменная модель

Сущности (в Postgres — snake_case, в C# — PascalCase):

- `profiles` — пользователь, IANA-таймзона, окна приёмов пищи
  (breakfast / lunch / dinner как локальное время)
- `medications` — название, форма, дозировка, единица, штрих-код (опц.),
  заметки
- `courses` — курс приёма: medication_id, дата начала, дата окончания или
  длительность, активен ли, привязка к диагнозу
- `schedules` — правило внутри курса:
  - тип: FixedTimes (в 08:00 и 20:00) | Interval (каждые 8 часов) |
    MealRelative (за 30 мин до завтрака) | AsNeeded (по потребности)
  - meal_relation: Before | With | After | Independent
  - offset_minutes (может быть отрицательным)
  - days_of_week или every_n_days
  - dose_amount
- `dose_events` — материализованное конкретное событие приёма.
  Это ядро системы. Поля: course_id, schedule_id, scheduled_at (timestamptz),
  local_date, state, taken_at, source, dedupe_key (unique)
- `inventory` — остаток по medication_id, порог для предупреждения
- `inventory_transactions` — append-only журнал списаний и пополнений
- `diagnoses` — диагноз, врач, дата, заметки
- `documents` — файл в Storage: bucket path, mime, размер, тип
  (анализ / рецепт / справка / выписка), привязки к diagnosis_id и/или course_id
- `messenger_links` — привязка канала: тип (telegram / discord), chat_id или
  channel_id, подтверждён ли, one-time link code
- `notification_deliveries` — журнал отправок: dose_event_id, канал,
  message_id, статус, попытки. Нужен для идемпотентности и для редактирования
  уже отправленного сообщения после подтверждения.

## Машина состояний dose_event

```
Scheduled ──> Notified ──> Taken
     │            │    └──> Skipped
     │            └──────> Missed   (по истечении окна)
     └──────────────────> Cancelled (курс удалён / приостановлен)
```

Правила, которые обязаны быть в Med.Domain и покрыты тестами:

1. Материализация: генерируем dose_events на горизонт 14 дней вперёд.
   Генерация идемпотентна — повторный запуск не создаёт дублей.
   Гарантия через `dedupe_key = schedule_id + scheduled_at`.
2. Часовые пояса: расписание хранится как локальное «настенное» время плюс
   IANA-таймзона. UTC-инстант вычисляется при материализации.
   Обязательные тесты: переход на летнее время (пропущенный час,
   удвоенный час), смена таймзоны пользователем, приём в 00:30.
3. Привязка к еде: MealRelative считается от окна приёма пищи из profile.
   Если пользователь сдвинул завтрак — будущие несозданные события
   пересчитываются, уже подтверждённые (Taken) не трогаются никогда.
4. Interval-расписания не переносятся при опоздании: пропущенная доза
   становится Missed, следующая остаётся на своём месте.
5. Окно подтверждения — настраиваемое, по умолчанию 3 часа. После него
   Notified → Missed автоматически.
6. Списание остатка происходит РОВНО при переходе в Taken, ровно один раз,
   и всегда через inventory_transactions. Никогда прямым UPDATE остатка.
   Повторное подтверждение того же события — no-op, не второе списание.
7. Отмена подтверждения (undo) создаёт компенсирующую транзакцию, а не
   удаляет прошлую.

# Планировщик и уведомления

Приложение НЕ является планировщиком. Клиент, который закрыт, ничего не
присылает. Поэтому:

- `pg_cron` раз в минуту вызывает Edge Function `tick`
- `tick` находит dose_events, у которых пришло время, и для каждого канала
  из messenger_links отправляет сообщение
- отправка идемпотентна: перед отправкой пишется строка в
  notification_deliveries; повторный tick не отправляет второй раз
- ретраи с экспоненциальной задержкой, лимит попыток, учёт 429 от Telegram

## Telegram

- Edge Function `telegram-webhook` принимает апдейты
- Сообщение с inline keyboard: «Принял», «Пропустить», «Отложить 15 мин»
- callback_query → обновление dose_event → answerCallbackQuery →
  editMessageText, чтобы кнопки исчезли и текст стал «Принято в 08:12»
- привязка чата: пользователь отправляет боту one-time код из приложения
- проверка secret_token у webhook обязательна

## Discord

Важное ограничение, не игнорируй его:
обычный Discord webhook не может отправлять интерактивные компоненты и не
может принимать нажатия. Поэтому:

- Основной режим: Discord Application (бот) плюс Interactions Endpoint URL,
  указывающий на Edge Function `discord-interactions`. Проверка Ed25519-
  подписи заголовков `X-Signature-Ed25519` и `X-Signature-Timestamp`
  обязательна, на невалидной подписи — 401. Кнопки работают.
- Режим деградации: если приложение Discord не настроено — обычный webhook,
  только текстовая доставка без кнопок. Подтверждение в этом случае идёт
  из Telegram или из GUI.

Спроектируй это за интерфейсом `INotificationChannel` с реализациями
`TelegramChannel`, `DiscordAppChannel`, `DiscordWebhookChannel`, чтобы
каналы добавлялись без правок доменного слоя.

# Синхронизация

Подтвердил на macOS, в Telegram, в Discord или на Android — во всех местах
статус обновился.

- Источник истины один: таблица dose_events в Postgres
- Клиенты подписаны на Supabase Realtime по своим строкам и обновляют UI
- Сообщения в мессенджерах редактируются по сохранённому message_id, когда
  подтверждение пришло из другого места
- Конфликты решаются по правилу: первое терминальное состояние побеждает,
  повторные попытки — no-op. Реализуй как условный UPDATE
  (`where state in ('Scheduled','Notified')`), а не read-modify-write

Офлайн: в v1 никакой офлайн-очереди записи. Только read-only кэш последнего
состояния, чтобы приложение открывалось без сети. Двусторонняя офлайн-
синхронизация — вне объёма, не изобретай её.

# Безопасность

- В клиентском приложении только anon key. `service_role` в клиенте —
  недопустимо ни при каких условиях
- RLS включён на каждой таблице, без исключений, политики по `auth.uid()`
- Токен Telegram-бота, ключи Discord, service_role живут только в переменных
  окружения Edge Functions
- Bucket с медицинскими файлами — приватный. Доступ только через signed URL
  с коротким TTL. Публичные ссылки на медфайлы запрещены
- В тексты сообщений в мессенджеры не попадают внутренние id, пути в Storage,
  трейсбеки и служебные детали
- Ни один секрет не попадает в репозиторий. Только `.env.example`

# Технический каркас UI

Avalonia, общий код представлений в Med.Ui, две head-сборки.
Экраны — минимальные, ровно чтобы проверить логику:

1. Сегодня — список dose_events на день, кнопки «Принял» / «Пропустить»
2. Лекарства — CRUD, остаток
3. Курсы и расписания — CRUD, включая MealRelative и Interval
4. Медкарта — диагнозы, список документов, загрузка файла, открытие по
   signed URL
5. Настройки — таймзона, окна приёмов пищи, привязка Telegram и Discord
   по one-time коду
6. Диагностика — журнал notification_deliveries, кнопка «прогнать tick
   вручную», состояние Realtime-подписки

Требования к каркасу: ItemsControl и TextBox без стилей, никакой вёрстки
«на будущее», никаких кастомных контролов. Каждый экран — ViewModel из
Med.Presentation плюс View, который только биндится. Навигация — простейший
switch по ViewModel.

  Тесты на DST, meal-relative, interval, окно пропуска, остатки.

- **Стадия 3** — Med.Infrastructure: репозитории на пакете Supabase, Auth,

- **Стадия 4** — Edge Functions: tick, telegram-webhook, discord-interactions.

- **Стадия 5** — Med.Presentation: ViewModels плюс тесты.
- **Стадия 6** — Med.Ui и head-проекты. Технический каркас экранов.

  Опиши шаги явно, включая подводные камни.

На каждой стадии сначала кратко изложи план и спорные места, дождись «ок»,
потом код.

# Definition of Done для каждой стадии

- решение собирается, тесты зелёные
- нет секретов в коде
- новые доменные правила покрыты тестами, включая границы времени
- в UI-слое нет бизнес-логики
- изменения схемы оформлены миграцией, а не правкой существующей

# Чего не делать

- не выносить логику в code-behind и не обращаться к Supabase из View
- не ставить планировщик в клиент и не полагаться на локальные таймеры
- не пытаться сделать «красиво» в UI — это отдельная будущая работа
- не добавлять зависимости, не перечисленные в стеке, без явного вопроса
- не изобретать офлайн-синхронизацию записи
- не отправлять компоненты через plain Discord webhook и не притворяться,
  что кнопки там работают
- не использовать локальные пуш-уведомления как основной канал: основной
  канал — Telegram и Discord
- не заглушать ошибки пустым catch
