## Введение и контекст

В рамках подготовки к выпуску версии **1.0.1** приложения **MedTracker** был проведён комплексный аудит всей кодовой базы проекта (.NET 10, C# 13/14, Avalonia 12.1.1, Supabase, SQLite, Android, macOS). 

Основная цель аудита:
- Проверить качество внедрения ранее выполненных 25 исправлений (FIX-001..FIX-025) и исключить наличие регрессий.
- Найти скрытые уязвимости, проблемы с утечками данных между локальными профилями, переполнением буферов, отказами уведомлений и утечками памяти.
- Предоставить чёткие, строго документированные рекомендации по исправлению каждого найденного дефекта.

Код в процессе аудита **не модифицировался**.

## Раздел 1: 🛡 Аудит безопасности

### 1.1 Инъекции и выполнение команд

#### [CRIT-03]: Регрессия экранирования AppleScript: крах уведомлений при наличии одинарной кавычки
- **Критичность**: 🔴 CRITICAL
- **Раздел аудита**: Безопасность и надёжность (1.1 Выполнение команд)
- **Файл**: `src/Med.Infrastructure/Notifications/LocalNotificationService.cs:183-184`
- **Описание**:
  В фиксе `FIX-001` метод `EscapeAppleScript` был модифицирован:
  ```csharp
  private static string EscapeAppleScript(string value) =>
      value.Replace("\\", "\\\\")
           .Replace("\"", "\\\"")
           .Replace("'", "\\'"); // <-- ОШИБКА
  ```
  В грамматике AppleScript строковый литерал ограничивается двойными кавычками `"..."`. Внутри двойных кавычек последовательность `\'` **не является валидным escape-символом** (в отличие от bash или C#). В AppleScript апостроф не требует экранирования.
  Если заголовок, текст уведомления или название лекарства содержат апостроф/одинарную кавычку (например: *"Doctor's note"*, *"Don't forget"*, *"It's time"*, название на иностранном языке или препарат в кавычках `'Тест'`), команда `osascript -e "display notification \"...\""` падает с фатальной синтаксической ошибкой:
  `Expected end of line but found unknown token (-2741)`.
- **Воздействие**:
  Уведомление о приёме жизненно важного препарата на macOS аварийно завершается с ненулевым кодом выхода, полностью подавляя нотификацию для пользователя.
- **Рекомендация**:
  Удалить замену `.Replace("'", "\\'")`. Строки в AppleScript требуют экранирования только символов `\` и `"`:
  ```csharp
  private static string EscapeAppleScript(string value) =>
      value.Replace("\\", "\\\\")
           .Replace("\"", "\\\"");
  ```

#### SQL Injection & Path Traversal
- **SQL Injection**: Проверены все вызовы в `src/Med.Infrastructure/LocalStorage/`. Все обращения к SQLite используют параметризованные команды (`AddWithValue("@param", ...)`). Прямая конкатенация строк в SQL отсутствует.
- **Path Traversal**: Метод `Document.BuildStoragePath` корректно использует `Path.GetFileName()` и валидирует отсутствие спецсимволов `..`, `/`, `\`.

### 1.2 Аутентификация и авторизация

#### [CRIT-04]: Неавторизованный публичный запуск Edge Function `tick` с правами Service Role
- **Критичность**: 🔴 CRITICAL
- **Раздел аудита**: Безопасность (1.2 Аутентификация и авторизация)
- **Файл**: `supabase/functions/tick/index.ts:22-25`
- **Описание**:
  Функция `tick` выполняет служебные операции по расписанию (материализация событий приёма, рассылка вебхуков, архивация просроченных доз) с использованием суперпользовательского ключа `SUPABASE_SERVICE_ROLE_KEY`. Проверка входящего запроса реализована так:
  ```typescript
  const authHeader = req.headers.get("Authorization");
  if (!authHeader || !authHeader.startsWith("Bearer ")) {
    return new Response(JSON.stringify({ error: "Missing or invalid bearer token" }), { status: 401 });
  }
  ```
  Функция проверяет **только сам факт наличия префикса `Bearer `**, но **не валидирует значение токена**. Любой внешний клиент, отправивший заголовок `Authorization: Bearer 12345`, успешно инициирует выполнение серверной фоновой процедуры.
- **Воздействие**:
  Отказ в обслуживании (DoS), истощение лимитов базы данных, неконтролируемая генерация записей и сбой таймингов уведомлений.
- **Рекомендация**:
  Сверять токен строго со значением сервисного ключа:
  ```typescript
  const token = authHeader.replace(/^Bearer\s+/i, "");
  const expectedKey = Deno.env.get("SUPABASE_SERVICE_ROLE_KEY");
  if (!expectedKey || token !== expectedKey) {
    return new Response(JSON.stringify({ error: "Unauthorized" }), { status: 401 });
  }
  ```

#### Секреты и JWT
- Файл `.env` надёжно внесён в `.gitignore` и отсутствует в Git-индексе.
- Hardcoded-секретов в кодовой базе C# не обнаружено.
- Класс `SupabaseOptionsValidator` гарантирует, что `SUPABASE_SERVICE_ROLE_KEY` не попадает в клиентскую конфигурацию.
- В `SupabaseAuthService.cs` refresh-токены маскируются при логировании.

### 1.3 Защита данных и изоляция пользователей

#### [CRIT-01]: Утечка медицинских данных между локальными профилями и в облако (Multi-User Data Leakage)
- **Критичность**: 🔴 CRITICAL
- **Раздел аудита**: Безопасность (1.3 Защита данных / 1.5 Миграция данных)
- **Файл**: `src/Med.Infrastructure/LocalStorage/LocalMedicationRepository.cs:20-38`, `LocalCourseRepository.cs:21-40`, `LocalInventoryRepository.cs:64-78`, `LocalDoseEventRepository.cs:215-235`, `DataMigrationService.cs:35-65`
- **Описание**:
  В таблицах SQLite колонка `user_id` заполняется при вставке записей, однако в методах чтения (`ListAsync()`, `ListByCourseAsync()`, `GetInventoryAsync()`) **отсутствует фильтрация по `user_id`**:
  ```csharp
  // LocalMedicationRepository.cs:20
  cmd.CommandText = "SELECT id, user_id, name, form, dosage, unit, ... FROM medications ORDER BY name ASC;";
  ```
  Это приводит к двум критическим проблемам:
  1. Если на одном устройстве приложением пользуются два человека в локальном режиме (или пользователь вышел и создал новый локальный профиль), новый пользователь сразу видит препараты, курсы и дозы предыдущего пользователя.
  2. В процессе миграции в облако `DataMigrationService.MigrateAsync` вызывает `_localMedications.ListAsync()`, вычитывает лекарства **всех** ранее сохранённых в SQLite пользователей и перезаписывает их `UserId = targetUserId`, загружая чужие медицинские данные в облачный аккаунт авторизовавшегося пользователя.
- **Воздействие**:
  Прямое нарушение законов о защите персональных медицинских данных (HIPAA / 152-ФЗ / GDPR). Утечка истории приёма чужих медикаментов.
- **Рекомендация**:
  1. Передавать идентификатор активного пользователя `userId` в методы локальных репозиториев (либо прокидывать контекст `IAuthService.CurrentUser` в `SqliteConnectionFactory`).
  2. Во всех запросах `SELECT`, `UPDATE` и `DELETE` добавить фильтрацию: `WHERE user_id = @user_id`.

#### [CRIT-02]: Подмена аватара и утечка личного фото между пользователями устройства
- **Критичность**: 🔴 CRITICAL
- **Раздел аудита**: Безопасность (1.3 Защита данных)
- **Файл**: `src/Med.Presentation/Shell/ShellViewModel.cs:347-368`
- **Описание**:
  При входе пользователя выполняется проверка наличия персонального файла аватара. Если файл не найден, срабатывает fallback-логика:
  ```csharp
  if (!File.Exists(avatarPath) && Directory.Exists(avatarDir))
  {
      var best = Directory.GetFiles(avatarDir)
          .OrderByDescending(File.GetLastWriteTimeUtc)
          .FirstOrDefault();
      if (best is not null)
      {
          File.Copy(best, avatarPath, overwrite: true);
      }
  }
  ```
  Приложение берёт файл аватара **любого другого пользователя**, у которого есть сохранённое фото на этом устройстве, и перезаписывает его как аватар текущего пользователя.
- **Воздействие**:
  Утечка биометрических/персональных данных: пользователь видит чужую фотографию, которая в дальнейшем синхронизируется с облаком как его собственная.
- **Рекомендация**:
  Полностью удалить блок `L348–360`. Если аватар для текущего `userId` не найден, устанавливать `AvatarPath = null; HasAvatar = false;`.

### 1.4 Платформенная безопасность (macOS / Android)

#### [CRIT-05]: Потеря всех запланированных уведомлений при перезагрузке Android (`RECEIVE_BOOT_COMPLETED`)
- **Критичность**: 🔴 CRITICAL
- **Раздел аудита**: Платформенная надёжность (1.4 / 2.4)
- **Файл**: `src/Med.Android/Properties/AndroidManifest.xml:13-20`, `src/Med.Android/NotificationReceiver.cs`
- **Описание**:
  Все алармы, зарегистрированные через `Android.App.AlarmManager`, полностью стираются операционной системой Android при перезагрузке устройства.
  В манифесте отсутствует разрешение `android.permission.RECEIVE_BOOT_COMPLETED`, и в проекте нет `BroadcastReceiver`, перехватывающего системное событие `android.intent.action.BOOT_COMPLETED`.
- **Воздействие**:
  После плановой или случайной перезагрузки телефона пользователь перестаёт получать любые напоминания о приёме лекарств, пока повторно не откроет приложение вручную. Для трекера медикаментов это означает пропуск жизненно важной терапии.
- **Рекомендация**:
  1. Объявить в `AndroidManifest.xml`:
     ```xml
     <uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
     ```
  2. Зарегистрировать ресивер `BootReceiver`, перепланирующий алармы на текущий день при запуске системы.

## Раздел 2: ⚡ Аудит производительности

### 2.1 Утечки памяти и управление ресурсами

#### [HIGH-01]: Утечка памяти из-за неотписываемой подписки на синглтон `IAuthService`
- **Критичность**: 🟠 HIGH
- **Раздел аудита**: Производительность (2.1 Утечки памяти)
- **Файл**: `src/Med.Presentation/Account/AccountViewModel.cs:43-61`, `src/Med.Presentation/Settings/SettingsViewModel.cs:54-61,171-174`
- **Описание**:
  В конструкторах `AccountViewModel` и `SettingsViewModel` выполняется подписка на событие `_auth.AuthStateChanged` через лямбда-выражение.
  - `AccountViewModel` не реализует `IDisposable`.
  - `SettingsViewModel` реализует `IDisposable`, но в `Dispose()` отписка от события отсутствует.
  Поскольку `IAuthService` зарегистрирован как `Singleton`, каждая созданная ViewModel навсегда удерживается в памяти через ссылку в списке делегатов синглтона.
- **Воздействие**:
  Постепенная деградация производительности, утечка памяти и выполнение лишних фоновых операций при смене статуса авторизации.
- **Рекомендация**:
  Реализовать `IDisposable` в `AccountViewModel`, использовать именованный метод-обработчик и отписываться в `Dispose()`:
  ```csharp
  _auth.AuthStateChanged -= OnAuthStateChanged;
  ```

### 2.2 Сетевые запросы и ввод-вывод (N+1, Realtime)

#### [HIGH-03]: Проблема N+1 запросов при загрузке расписания и лекарств
- **Критичность**: 🟠 HIGH
- **Раздел аудита**: Производительность (2.2 Сетевые запросы)
- **Файл**: `src/Med.Application/UseCases/GetDayAgendaUseCase.cs:83-89`, `src/Med.Presentation/Medications/MedicationsViewModel.cs:344-346`
- **Описание**:
  В `GetDayAgendaUseCase` итеративно для каждого курса отправляется отдельный сетевой запрос к базе данных:
  ```csharp
  foreach (var courseId in activeCourseIds)
  {
      var courseSchedules = await schedules.ListByCourseAsync(courseId, ct);
      ...
  }
  ```
  Если у пользователя 15 курсов, приложение делает 15 отдельных HTTP-запросов к REST API Supabase / SQLite.
- **Воздействие**:
  Задержки отображения экрана «Сегодня» до 2-3 секунд на мобильном интернете, избыточная нагрузка на сеть.
- **Рекомендация**:
  Добавить метод пакетной выборки в `IScheduleRepository`:
  ```csharp
  Task<IReadOnlyList<Schedule>> ListByCourseIdsAsync(IReadOnlyList<Guid> courseIds, CancellationToken ct = default);
  ```

#### [HIGH-05]: Отсутствие Jitter и риск рекурсивного зацикливания при переподключении Realtime
- **Критичность**: 🟠 HIGH
- **Раздел аудита**: Производительность и надёжность сети (2.2)
- **Файл**: `src/Med.Infrastructure/Supabase/Realtime/SupabaseEntityRealtimeSync.cs:105-115,140-172`
- **Описание**:
  1. Задержка переподключения `delaySeconds = Math.Min(60, Math.Pow(2, _retryAttempt))` не содержит случайного фактора (jitter).
  2. Метод `ScheduleReconnect()` вызывает `StartAsync()`. Если в `StartAsync` происходит ошибка, его блок `catch` снова вызывает `ScheduleReconnect()`, что при сбоях может приводить к реентерабельным наложениям задач.
- **Воздействие**:
  Эффект «громоподобного стада» (thundering herd) на серверы Realtime и нестабильная работа клиента при обрывах связи.
- **Рекомендация**:
  Добавить рандомизированный джиттер (80-120%) и исключить взаимный рекурсивный вызов между `StartAsync` и `ScheduleReconnect`.

### 2.4 Планирование уведомлений

#### [HIGH-04]: Нестабильный рандомизированный хэш и риск `OverflowException` в Android Notification ID
- **Критичность**: 🟠 HIGH
- **Раздел аудита**: Надёжность Android (2.4)
- **Файл**: `src/Med.Android/AndroidNotificationService.cs:100,142`
- **Описание**:
  Код вычисляет ID уведомления:
  ```csharp
  var notificationId = Math.Abs(id.GetHashCode());
  ```
  1. В .NET 8/9/10 реализация `string.GetHashCode()` рандомизируется при каждом запуске приложения. При перезапуске приложения `CancelScheduled(id)` вычисляет совершенно другой хэш и не может отменить старый аларм.
  2. Если хэш окажется равен `int.MinValue`, вызов `Math.Abs(int.MinValue)` выбросит `System.OverflowException`.
- **Воздействие**:
  Аварийное падение приложения при совпадении хэша с `int.MinValue` и зависание неотменяемых дублирующихся алармов.
- **Рекомендация**:
  Использовать детерминированный стабильный алгоритм хэширования на базе байтов GUID или FNV-1a.

## Раздел 3: 🧹 Аудит чистоты и корректности кода

### 3.1 Доменная модель, инварианты и состояние

#### [HIGH-02]: Рассинхронизация остатков: отсутствие списания со склада в локальном режиме
- **Критичность**: 🟠 HIGH
- **Раздел аудита**: Корректность доменной логики (1.5 / 3.1)
- **Файл**: `src/Med.Infrastructure/LocalStorage/LocalDoseTransitionService.cs:25-56`
- **Описание**:
  В облачном режиме подтверждение приёма дозы (`confirm_dose`) уменьшает остаток препарата на складе. В локальном режиме `LocalDoseTransitionService` обновляет только статус события `dose_events`, полностью игнорируя складской учёт.
- **Воздействие**:

- **Рекомендация**:
